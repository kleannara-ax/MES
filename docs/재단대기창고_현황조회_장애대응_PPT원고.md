# 슬라이드 1. 재단대기창고 현황조회 장애 대응

**재단대기창고 현황조회 장애 대응**

바코드 미표시와 상세조회 오류의 원인 및 처리 절차

운영 인수인계

## 시각 구성

- 제목을 화면 중앙에 크게 배치
- 하단에 `대상 화면: POP_INV04 / WRK35` 표기
- 배경에는 재단대기창고 화면 캡처를 흐리게 사용

## 발표자 메모

이 자료는 재단대기창고 화면에서 바코드가 보이지 않거나, 바코드는 보이지만 상세정보가 열리지 않을 때 사용하는 장애 대응 자료입니다. 이번 실제 사례를 기준으로 화면 조회 조건, SAP 인터페이스, 데이터 정합성 확인 순서를 설명합니다.

# 슬라이드 2. 증상은 두 가지로 구분

## 화면 문구

### 증상 A

**바코드가 목록에 보이지 않음**

재고 테이블의 화면 표시 조건을 만족하지 못한 경우

### 증상 B

**목록에는 보이지만 상세정보가 열리지 않음**

재고는 존재하지만 작업실적 또는 작업지시 조건을 만족하지 못한 경우

### 핵심

목록조회와 상세조회는 서로 다른 데이터를 확인한다

## 시각 구성

- 화면을 좌우로 나누어 증상 A와 증상 B 비교
- 하단에 `목록: TB_INV001`, `상세: TB_WRK002 + 작업지시` 표시

## 발표자 메모

두 증상을 반드시 구분해야 합니다. 목록은 현재고인 `TB_INV001`을 중심으로 조회합니다. 상세정보는 생산실적 `TB_WRK002`와 작업지시 테이블까지 확인합니다. 따라서 목록에 보인다는 사실만으로 정상 실적이라고 판단할 수 없습니다.

# 슬라이드 3. 목록에 표시되는 조건

## 화면 문구

**재단대기창고 목록의 기본 조건**

| 항목 | 정상 표시값 |
|---|---|
| 플랜트 | `WERKS = P100` |
| 저장위치 | `STOR_LOC_CD = 2700` |
| 재고수량 | `STCK_QTY > 0` |
| 재고상태 | `STCK_STA = 00` |
| 로케이션 | `MR01 ~ MR45` |

조건 하나라도 맞지 않으면 화면에 표시되지 않을 수 있다

## 발표자 메모

재단대기창고 화면은 `TB_INV001`의 모든 데이터를 보여 주지 않습니다. 저장위치 `2700`에 있으며 수량이 0보다 크고 재고상태가 `00`인 데이터가 주요 조회 대상입니다. `MR41`은 별도 특수 조건이 아니라 `MR01~MR45` 중 하나의 로케이션입니다.

## 확인 SQL

```sql
SELECT WERKS, IND_BCD, LOT_NO, ORDER_NO,
       STOR_LOC_CD, LOC_CD, STCK_QTY, STCK_STA, DLFL
FROM KNRAMES.TB_INV001
WHERE IND_BCD = '확인할 바코드';
```

# 슬라이드 4. 상세정보 조회 조건

## 화면 문구

**상세정보는 정상 작업실적만 조회**

| 확인 대상 | 필수 조건 |
|---|---|
| 생산실적 | `TB_WRK002`에 바코드 존재 |
| 작업지시 | 작업지시번호와 순번 일치 |
| 취소 여부 | `CNL_YN`이 `Y`가 아님 |
| 후속 작업지시 | `TB_SCH017.USE_YN = Y` |

취소된 생산실적은 상세조회 대상에서 제외된다

## 발표자 메모

상세정보 팝업은 `SP_POP_WRK81_S01`을 호출합니다. 이 프로시저는 `NVL(TB_WRK002.CNL_YN, 'N') = 'N'` 조건을 사용합니다. 취소된 실적은 `CNL_YN='Y'`이므로 조회 결과가 없어지고 화면에는 `작업지시 정보를 찾지 못했습니다.`가 나타납니다.

# 슬라이드 5. 이번 장애의 직접 원인

## 화면 문구

**취소 실적의 재고가 창고에 남아 있었다**

| 데이터 | 상태 |
|---|---|
| `TB_WRK002` | 기존 실적 취소 `CNL_YN = Y` |
| `TB_INV001` | 기존 바코드 재고가 가용상태로 잔존 |
| 목록조회 | 재고가 있으므로 화면에 표시 |
| 상세조회 | 취소 실적이므로 조회에서 제외 |

### 화면 메시지

`작업지시 정보를 찾지 못했습니다.`

## 시각 구성

- 가운데에 `목록 표시`와 `상세조회 실패`를 대비
- 데이터 불일치 지점인 `TB_WRK002`와 `TB_INV001`을 강조

## 발표자 메모

화면 프로그램 자체의 오류라기보다 테이블 상태가 서로 맞지 않은 사례입니다. 생산실적 테이블에서는 취소되었지만 재고 테이블에는 기존 바코드가 정상재고처럼 남았습니다. 그 결과 목록과 상세조회가 서로 다른 판단을 했습니다.

# 슬라이드 6. 기존 실적과 신규 실적

## 화면 문구

| 작업오더 | LOT | 기존 바코드 | 기존 확정 | 신규 바코드 | 신규 확정 |
|---|---|---|---|---|---|
| `1112882924` | `6910M30393` | `26910M0403` | `0013129111 / 01` | `26910M0423` | `0013129111 / 03` |
| `1112882923` | `6910M30395` | `26910M0405` | `0013129110 / 01` | `26910M0425` | `0013129110 / 03` |

### 판단 근거

- 작업오더와 LOT가 동일
- 작업지시번호와 순번이 동일
- 기존 실적 취소 후 신규 바코드 등록
- 신규 실적은 취소되지 않음

## 발표자 메모

신규 바코드는 번호 패턴으로 추정한 것이 아닙니다. 기존 바코드와 작업오더, LOT, 작업지시, 품목, 수량이 같고 등록시간이 더 늦었습니다. 기존 실적은 취소되었고 신규 실적은 정상 상태였습니다. SAP 확정카운터도 `01`에서 `03`으로 변경되었습니다.

# 슬라이드 7. SAP 인터페이스 확인

## 화면 문구

| 처리 | 인터페이스 | 테이블 | 확인 항목 |
|---|---|---|---|
| 생산실적 확정 | `MES_IF_126` | `TB_IFS004` | `ZRESULT`, `RUECK`, `RMZHL` |
| 생산실적 취소 | `MES_IF_129` | `TB_IFS007` | 취소 대상과 SAP 응답 |
| 제품입고 | `MES_IF_130` | `TB_IFS008` | 자재문서번호와 처리 결과 |

### 성공 기준

`ZRESULT = S`

MES 작업실적과 SAP 확정번호·카운터가 일치해야 한다

## 발표자 메모

신규 실적의 정상 여부는 `TB_WRK002`만으로 판단하면 안 됩니다. `TB_IFS004`에서 생산실적 확정 성공 여부를 확인하고, `TB_IFS008`에서 제품입고 성공 여부를 확인해야 합니다. 작업실적의 `SDOC_NO`, `SDOC_SEQNO`는 인터페이스의 `RUECK`, `RMZHL`과 일치해야 합니다.

# 슬라이드 8. 확정수량이 없음의 의미

## 화면 문구

**SAP 메시지**

`확정수량이 없음`

### 의미

SAP가 지정된 확정번호와 카운터에서 취소할 잔여수량을 찾지 못함

### 주요 원인 후보

- SAP에서 이미 취소 처리
- 다른 경로에서 먼저 취소
- 확정카운터 불일치
- 최초 확정이 정상 완료되지 않음
- MES와 SAP의 취소수량 불일치

## 발표자 메모

이 메시지는 MES에 생산수량이 없다는 뜻이 아닙니다. SAP가 취소 요청을 받은 시점에 해당 `RUECK + RMZHL` 조합에서 취소할 수량을 찾지 못했다는 뜻입니다. 이번 사례의 취소 인터페이스는 `MES_IF_129`, 테이블은 `TB_IFS007`입니다.

# 슬라이드 9. 장애 확인 순서

## 화면 문구

1. `TB_INV001`에서 화면 표시 조건 확인
2. `TB_WRK002`에서 실적과 취소 여부 확인
3. 동일 작업오더·LOT의 후속 바코드 확인
4. `TB_IFS004`에서 신규 실적 확정 성공 확인
5. `TB_IFS008`에서 제품입고 성공 확인
6. `TB_IFS007`에서 기존 실적 취소 결과 확인
7. SAP 담당자에게 기존 확정의 현재 상태 확인
8. 구 바코드와 신규 바코드의 이중재고 확인

## 시각 구성

- 8단계를 세로 흐름도로 구성
- DB 확인 단계와 SAP 확인 단계를 색상으로 구분

## 발표자 메모

재고부터 시작해 작업실적, 신규 인터페이스, 취소 인터페이스 순서로 확인합니다. 마지막에는 반드시 SAP 담당자에게 기존 확정번호와 카운터의 실제 상태를 확인해야 합니다. 화면 데이터만 보고 SAP 처리를 추정해서는 안 됩니다.

# 슬라이드 10. 안전한 대응 원칙

## 화면 문구

### 처리 방향

- 신규 정상 바코드는 유지
- SAP 상태를 확인한 뒤 기존 잔존재고 정합성 처리
- 실패한 취소 인터페이스는 재전송 여부를 별도 판단
- 화면 재조회와 상세조회로 최종 확인

### 금지사항

- `CNL_YN` 임의 변경
- `ZRESULT`를 `N`으로 바꾼 뒤 무조건 재전송
- `TB_INV001` 직접 삭제
- SAP 확인 없이 확정번호 수정

### 완료 기준

기존 취소 바코드는 가용재고에서 제외되고 신규 바코드만 정상 조회된다

## 발표자 메모

운영 데이터는 화면만 정상으로 보이게 수정하면 안 됩니다. SAP 상태 확인과 운영 DBA 승인을 먼저 받아야 합니다. 보정 후에는 목록에서 기존 바코드가 사라졌는지, 신규 바코드가 남아 있는지, 신규 상세정보가 정상적으로 열리는지 확인합니다.

# 부록 1. 구·신규 바코드 비교 SQL

```sql
SELECT
    I.ORDER_NO,
    I.LOT_NO,
    I.IND_BCD,
    I.STOR_LOC_CD,
    I.LOC_CD,
    I.STCK_QTY,
    I.STCK_STA,
    I.DLFL,
    W.PRFM_QTY,
    W.CNL_YN,
    W.CNL_RMK,
    W.SDOC_NO,
    W.SDOC_SEQNO
FROM KNRAMES.TB_INV001 I
LEFT JOIN KNRAMES.TB_WRK002 W
       ON W.WERKS = I.WERKS
      AND W.IND_BCD = I.IND_BCD
WHERE I.WERKS = 'P100'
  AND I.IND_BCD IN (
      '26910M0403', '26910M0405',
      '26910M0423', '26910M0425'
  )
ORDER BY I.ORDER_NO, I.IND_BCD;
```

# 부록 2. 후속 실적 검색 SQL

```sql
WITH OLD_DATA AS (
    SELECT WERKS, IND_BCD, ORDER_NO, LOT_NO,
           WRK_ORDR_NO, WRK_ORDR_SEQNO, REGDATE
    FROM KNRAMES.TB_WRK002
    WHERE WERKS = 'P100'
      AND IND_BCD IN ('26910M0403', '26910M0405')
)
SELECT
    O.IND_BCD AS ORIGINAL_IND_BCD,
    W.IND_BCD,
    W.ORDER_NO,
    W.LOT_NO,
    W.CNL_YN,
    W.SDOC_NO AS RUECK,
    W.SDOC_SEQNO AS RMZHL,
    W.REGDATE
FROM OLD_DATA O
JOIN KNRAMES.TB_WRK002 W
  ON W.WERKS = O.WERKS
 AND W.ORDER_NO = O.ORDER_NO
 AND W.LOT_NO = O.LOT_NO
 AND W.WRK_ORDR_NO = O.WRK_ORDR_NO
 AND W.WRK_ORDR_SEQNO = O.WRK_ORDR_SEQNO
ORDER BY O.IND_BCD, W.REGDATE;
```
